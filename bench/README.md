# Java vs Rust benchmark

Compares the Java service (`src/`, Spring Boot 4 + Spring Data JPA on Tomcat, port 9966) with the
Rust port (`rust-petclinic/`, Axum + sqlx, port 9977) on the **same PostgreSQL** (docker compose
`postgres` profile, the Java repo's `schema.sql` + `data.sql`) and the **same traffic mix**:

| share | request                                 |
|------:|-----------------------------------------|
|  40 % | `GET /petclinic/api/owners/{id}`        |
|  20 % | `GET /petclinic/api/owners?lastName=…`  |
|  15 % | `GET /petclinic/api/vets`               |
|  10 % | `GET /petclinic/api/pettypes`           |
|  10 % | `GET /petclinic/api/pets/{id}`          |
|   5 % | `POST /petclinic/api/owners`            |

Load is generated by [k6](https://k6.io) (`grafana/k6` Docker image on the host network,
script `k6/mix.js`). Per service the script runs:

1. start the service and time the first `200` from `/petclinic/actuator/health` (**startup**);
2. **warm-up**: 30 s at 500 req/s (JIT, connection pools, caches – not measured);
3. **fixed rate**: 60 s at 500 req/s (`constant-arrival-rate`). CPU, memory, latency and the number
   of SQL statements per request are measured here, sampled every second;
4. **peak**: 30 s with 64 concurrent connections and no rate cap (`constant-vus`) → peak throughput.

Measurements come from the process itself, not from the load tool: CPU is `utime + stime` of the
service PID from `/proc/<pid>/stat` (all JVM threads included), memory is `VmRSS` / `VmHWM` from
`/proc/<pid>/status`, SQL statements per request from `pg_stat_statements` (reset after the
warm-up, divided by the k6 request count; the field is omitted if the extension cannot be
enabled). Latency percentiles are k6's `http_req_duration`.

Cost: `cpuSecondsPerMillionRequests / 3600 * vcpuHourUsd`, `vcpuHourUsd = 0.0509` by default
(AWS eu-central-1 c7i on-demand, per vCPU-hour; override with `VCPU_HOUR_USD`).

## Run it

```bash
# Linux with docker (compose v2), cargo, java 17+, python3, jq, curl, bc
bench/run.sh                 # builds the jar (./mvnw) and the Rust binary, runs everything
SKIP_BUILD=1 bench/run.sh    # reuse target/*.jar and rust-petclinic/target/release
RATE=1000 DURATION=120 PEAK_DURATION=60 CONCURRENCY=128 bench/run.sh
SERVICES=rust bench/run.sh   # one side only
```

If Maven Central rate-limits your host (HTTP 429), point the wrapper at a mirror:
`MVNW_REPOURL=https://maven-central-eu.storage-download.googleapis.com/maven2 bench/run.sh`.

Outputs in `results/`:

| file                           | content                                                                   |
|--------------------------------|---------------------------------------------------------------------------|
| `summary.json`                 | aggregate numbers per service (schema below)                              |
| `timeseries.json`              | per-second samples (`cpuCores`, `rps`, `p50Ms`, `p99Ms`, `rssMb`) of the fixed-rate phase, plus `peakSamples` |
| `run.log`                      | plain-text log of the run, one line per second during the measured phases |
| `parity.txt`                   | output of `bench/parity.sh` (JSON parity of every ported endpoint)         |
| `raw/<svc>-{warmup,fixed,peak}.json` | k6 end-of-test summaries                                           |
| `raw/<svc>-*-per-second.json`  | per-second aggregates produced by `k6/aggregate.py`                        |
| `raw/<svc>-process.json`       | CPU seconds, RSS, startup, `pg_stat_statements` calls                      |
| `raw/<svc>-service.log`        | stdout/stderr of the service during the run                               |

`summary.json` keeps these names verbatim (the UI in `frontend/` reads them):
`measuredAt`, `host`, `runs`, `vcpuHourUsd`, `workload.{ratePerSecond,durationSeconds,peakConcurrency,mix}`,
`services.{java,rust}.{label,cpuCoresAtFixedRate,cpuSecondsPerMillionRequests,costPerMillionRequestsUsd,peakRequestsPerSecond,p50Ms,p99Ms,memoryMb,startupSeconds,dbQueriesPerRequest,failedRequests}`.

## Parity

`bench/parity.sh` fetches every ported endpoint from both services (several ids, the `404` and
error paths, `POST /owners`), normalises key order with `jq -S` and exits non-zero on any
difference. Last run: see [`results/parity.txt`](results/parity.txt).

## Results

| metric | Java (Spring Boot 4, JPA) | Rust (Axum, sqlx) | Java / Rust |
|---|---:|---:|---:|
| CPU at 500 req/s (cores) | 0.363 | 0.105 | 3.5× |
| CPU seconds per 1M requests | 725 | 210 | 3.5× |
| Cost per 1M requests (USD, c7i vCPU) | 0.0103 | 0.003 | 3.4× |
| Peak throughput, 64 connections (req/s) | 5254 | 8634 | 1.6× |
| p50 latency at 500 req/s (ms) | 1.1 | 1 |  |
| p99 latency at 500 req/s (ms) | 3.7 | 4 |  |
| p99 latency at peak (ms) | 38.2 | 14.9 | 2.6× |
| Peak RSS (MB) | 845 | 21 | 40.2× |
| Startup until health = UP (s) | 5.45 | 0.01 |  |
| SQL statements per request | 4.5 | 1 | 4.5× |
| Failed requests | 0 | 0 |  |

Measured on 2026-11-03T20:53:55Z on this machine: Intel(R) Xeon(R) Processor, 8 cores (a shared cloud VM, postgres 16.3 in Docker, k6 and both services on the same host). One run (`runs: 1`), 30 s warm-up, 60 s at 500 req/s, 30 s at 64 connections.

Caveats, so nobody over-reads these numbers:

* The host is noisy. Per-second CPU of the Java service at 500 req/s ranged from 0.266 to 0.997 cores (mean 0.362); Rust from 0.089 to 0.21 (mean 0.106). See `results/timeseries.json`.
* The load generator and PostgreSQL run on the same 8 cores as the service under test, so the peak phase measures the whole box, not the service alone; the fixed-rate phase (CPU per request) is the number to quote.
* At 500 req/s both services are far from saturation, so p50/p99 are within a millisecond of each other; the difference is CPU (and therefore cost) and memory, not latency.
* `dbQueriesPerRequest` counts statements seen by `pg_stat_statements` during the fixed-rate phase divided by k6 requests. On this fork Spring Data JPA issues 4.5 statements per request on this mix (owner lookups fetch pets, visits and types in separate selects); the Rust service issues one joined statement per request.
* Startup is measured from process start to the first `200` on `/petclinic/actuator/health`; the JVM number includes Hibernate boot and the schema/data initialisation the `postgres` profile performs.
